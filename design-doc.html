01

Overview

Menagerie stops being an app you install and becomes a workspace you sign into — pets.shaoor-ai.com, deployed and billed the same way as its sibling construct.shaoor-ai.com, on the same Vercel account and the same Supabase project. The product idea is unchanged: one longitudinal record for every animal and habitat a household keeps, with costs and visits scoped to an individual, a group, or the whole home. What changes is that the household is now a tenant — a billable workspace with a plan, a trial clock, and seats for the people who care for its animals.

Species-agnostic core

Cats, dogs, birds, reptiles, and aquarium habitats share one schema of pets, groups, habitats, vets, and expenses — no per-species tables to maintain.

Multi-tenant from the start

Every table carries a tenant_id and Row Level Security policy on day one — not retrofitted after the first paying workspace signs up.

Trial-led growth

Every workspace starts on a 14-day trial of the top consumer tier — no card required — and downgrades gracefully to Litter (free) rather than locking anyone out.

02

The market gap

Pet-care software today is built around one species and one animal at a time. Menagerie's gap is unchanged by the SaaS pivot — it's now sharper, because a subscription product can price and package around it directly.

What exists

Single-pet trackers (one dog, one profile), vet-practice portals tied to one clinic, and spreadsheet habits for anyone with a mixed household — a cat, a reef tank, and a foster litter tracked in three different places, none of them sharing a cost ledger.

What pets.shaoor-ai.com sells

One workspace, unlimited species, with costs and care events scoped to a pet, a group ("The Persians"), a habitat ("The Reef Tank"), or the whole household — and, unique to a SaaS packaging, a workspace type built for rescues and shelters, who today have no equivalent of Menagerie at any price.

Differentiators that only exist because this is a subscription product
  • Org-tier workspaces. A shelter or breeder tenant gets the same core record per animal, plus adoption-ready public profiles and multi-seat staff access — impossible to sustain as a free app, viable as a priced tier.
  • Multi-household tenants. A Sanctuary-tier workspace can hold more than one physical home (a family that splits pets between two houses, a foster network) under one billing relationship and one shared cost ledger.
  • Shared infrastructure economics. Riding shaoor-ai.com's existing Supabase and Vercel accounts means the product breaks even at a fraction of the subscriber count a standalone SaaS would need.
03

Modeling for any species

Unchanged from the original design: species is a free-text field on pets, not an enum or a table-per-species split. A habitat (aquarium, terrarium, coop) is a first-class sibling of a pet, not a bolted-on aquarium feature — so a tank's water changes and a cat's baths both write to the same care_tasks table with a polymorphic scope.

Habitats are peers of pets

Vet visits, expenses, gallery media, and comments all attach to either a pet_id or a habitat_id — the app layer never assumes an event is about an individual animal.

Three-level scoping, everywhere

Shopping line items, expenses, and care tasks each carry a scope_type of pet, group, or household (now: tenant) — a joint vet trip for two kittens costs once, scoped to the group, never split awkwardly across two pet ledgers.

04

Multi-tenant architecture

One Supabase project, one Postgres database, shared with construct.shaoor-ai.com and whatever else lives on shaoor-ai.com — Menagerie gets its own schema (menagerie), not its own database and not a schema-per-tenant split. Isolation between workspaces is enforced by Postgres Row Level Security, not by infrastructure boundaries.

Dedicated schema, shared database

All product tables live under menagerie.* in the same Postgres instance that backs shaoor-ai.com. auth.users and Supabase Auth are shared platform-wide — a person can hold one login across every shaoor-ai.com product.

Row Level Security, not app-layer filtering

Every tenant-scoped table has ENABLE ROW LEVEL SECURITY and a policy resolving tenant_id against the caller's memberships — a bug in a Next.js route can never leak another workspace's rows.

Workspace = tenant = household

The old "Household" entity becomes tenants directly — it already was the natural unit of billing and sharing; the SaaS rebuild formalizes it rather than adding a parallel concept above it.

Membership & roles

A tenant can hold several people (a couple, a shelter's staff). memberships joins auth.users to tenants with a role:

owner
Created the workspace, manages billing, can remove any member, one per tenant minimum.
caregiver
Full read/write on pets, health, shopping, tasks, and gallery. Cannot touch billing or remove other members.
viewer
Read-only — for a pet-sitter, a co-parent who just wants visibility, or a vet given temporary access to one workspace's health history.
The RLS pattern, concretely
-- one helper, reused by every policy in the schema
create function menagerie.my_tenant_ids()
returns setof uuid language sql stable security definer as $$
  select tenant_id from menagerie.memberships where user_id = auth.uid()
$$;

alter table menagerie.pets enable row level security;

create policy "tenant isolation - select"
  on menagerie.pets for select
  using (tenant_id in (select menagerie.my_tenant_ids()));

create policy "tenant isolation - write"
  on menagerie.pets for insert with check (tenant_id in (select menagerie.my_tenant_ids()))
  ;
-- repeated verbatim (swap the table name) for every tenant-scoped table:
-- pets, pet_groups, habitats, vets, vet_visits, illnesses, vaccinations,
-- grooming_visits, products, shopping_orders, care_tasks, feeding_logs,
-- media, comments, expenses

One security definer function keeps every policy a one-liner and means a new tenant-scoped table is three lines of migration, not a bespoke policy design each time.

The Stripe flow
Sign up → trialing → Stripe Checkout (add card) → webhook: customer.subscription.updated → subscriptions row upserted → Customer Portal for changes/cancel

A Vercel Route Handler at /api/stripe/webhook is the only writer of menagerie.subscriptions — the app never trusts client-side plan state, only what Stripe confirms. Trial expiry is a Vercel Cron job that flips any trialing row past trial_ends_at with no payment method to tenants.plan_code = 'litter'.

06

Stack & deployment

Deliberately unoriginal: reuse every default construct.shaoor-ai.com already made, so the only new infrastructure decision is the Supabase schema and the Stripe product catalog.

Frontend
Next.js (App Router) on Vercel — a separate Vercel project ("pets"), sibling to the "construct" project, both under the shaoor-ai.com team/account.
Domain
pets.shaoor-ai.com as a CNAME in the same DNS zone that already routes construct.shaoor-ai.com — added as a Vercel domain on the new project, no zone changes needed.
Database
The existing shaoor-ai.com Supabase project, new menagerie schema, RLS on every tenant-scoped table (see §04).
Auth
Supabase Auth, shared auth.users — a person who already has a shaoor-ai.com login can accept a workspace invite without creating a second account.
Billing
Stripe Checkout + Customer Portal; a `plans` table mirrors Stripe Price IDs so pricing changes are a database update, not a redeploy.
Media
Supabase Storage, one bucket per tenant prefix (media/{tenant_id}/...), signed URLs — gallery photos and vet-visit attachments never sit on a public path.
Jobs
Vercel Cron: nightly vaccination/reminder digest, trial-expiry downgrade sweep, weekly expense-summary email.
07

Tenancy-first ERD

Four new tables sit above the existing pet-care schema and gate every row below them with a tenant_id. Everything from §03 of the original design — pets, groups, habitats, vets, health, shopping, care tasks, gallery — is unchanged in shape; only household_id is renamed tenant_id and gains its RLS policy.
